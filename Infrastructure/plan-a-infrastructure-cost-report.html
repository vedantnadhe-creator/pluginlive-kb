What Plan A changes

Included

  • Move DEV and UAT PostgreSQL onto their existing application VMs, retiring one database VM per environment.
  • Use OCI Resource Scheduler to stop non-production compute overnight and on weekends, with an on-demand override.
  • Right-size Kubernetes pod CPU and memory requests from measured utilisation, then reduce OKE worker capacity from five nodes to three.
  • Move static websites from always-on VMs to OCI Object Storage static hosting.
  • Move managed PostgreSQL to a self-managed PostgreSQL 16 deployment on an OCI A1 VM, following migration and restore tests.
  • Move OKE from Enhanced to Basic only after confirming required features, support posture, and operational ownership.
  • Prune unused OCIR container images; the identified image footprint is approximately 407 GB.
  • Use KEDA only for idle queue/admin workers so background capacity can fall to zero when there is no work.

Explicitly protected / not included

  • No scale-to-zero for the live exam path: login, session, questions, autosave, submission, proctoring, database, and cache stay warm.
  • No production database cutover without tested backup restoration, performance testing, and a rollback route.
  • No reduction in required production availability or candidate experience targets.
  • No assumption that KEDA alone removes VM cost; node cost falls only when empty capacity can safely scale in.

Environment-by-environment plan

DEV · Week 0–1

Make development disposable outside working hours

Consolidate PostgreSQL onto the existing DEV application VM, then schedule the environment off from 12am–7am and throughout weekends. Preserve a one-click manual start for developers. Clean unused OCI Registry images.

UAT · Week 0–1

Mirror the DEV saving without blocking QA

Apply the same VM consolidation and off-hours schedule, while retaining an override for planned test windows and release validation. Validate database performance after consolidation before retiring the UAT DB VM.

PROD · Week 2–7

Reduce fixed capacity, not service reliability

First set realistic pod requests using observed load. Reduce worker nodes only after scheduling and load-test evidence supports it. Migrate static content and PostgreSQL in reversible stages, and reserve KEDA scale-to-zero for asynchronous work only.

Production guardrails

The live assessment experience is the constraint that governs every production saving. Cost changes are accepted only when these guardrails pass.

  • Minimum replicas and capacity remain for all candidate-facing paths.
  • Load tests cover peak concurrent exams, autosave, submission, and proctoring.
  • Database backup restoration and rollback are rehearsed before cutover.
  • Metrics, alerts, and a named rollback owner are in place for each production phase.
