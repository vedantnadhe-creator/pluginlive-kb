Why Plan A wins on the numbers. The comparison reduces to one ratio: an always-on vCPU costs ₹584/month on OCI Ampere A1 and roughly ₹6,900/month on Cloud Run in Mumbai — about 12×. The workload needs 4–5 permanently warm cores (auth, student, the AI/proctoring service, the queue workers). Serverless only beats a cheap ARM VM below roughly 10% duty cycle — and the parts of the estate that are that idle (DEV, UAT, the builder, batch jobs) can simply be switched off on a schedule, for free. Where Plan B genuinely wins is not cost: non-production becomes almost free, there is no cluster or database to operate, and on/off is native rather than assembled. If the binding constraint were engineering time rather than money, Plan B would be the better answer.

Phase 0 — already executed

Common to every plan and complete since 17 August 2026. ₹44,000/month banked

What was removed

The production database was cut over to pl-prod-pg16 on 31 July, but the previous PostgreSQL 14 system — two instances of 2 OCPU / 32 GB — kept running in parallel with nothing connected to it.

  • Zero client connections; 2 inserts / 3 updates / 0 deletes across 8 days
  • Data had diverged by 295 students and 5,629 assignment records — a frozen snapshot, never a fallback
  • Zero references in configmaps, secrets, deployments, cronjobs or Grafana across all 10 namespaces

Archived before deletion

  • Logical dump — 2.17 GB, pg_restore -l verified at 2,603 objects, private bucket pl-prod-db-archive
  • Manual system backup — 1 GB, 35-day retention, covering the four legacy side-databases
  • Post-deletion: all pods Running, no new restarts, live database writing normally

Side-fix: three read-only helper scripts had been querying the frozen host since 3 August, silently returning stale production data. All repointed.

Plan A in detail — the recommended route

Everything stays on OCI, in Mumbai. The saving comes entirely from matching capacity to measured load, and from switching capacity off when it is genuinely not needed.

Target architecture

  • PROD — OKE Basic cluster (free control plane); 2 × A1 4 OCPU/24 GB baseline nodes always on; 1 preemptible calendar-driven burst node (~40 h/month); self-managed PostgreSQL 16 on A1 4/24 with PgBouncer
  • Frontends — OCI Object Storage behind the existing Flexible Load Balancer
  • DEV / UAT — one VM each, database merged in, Resource Scheduler off nights and weekends
  • Batch — parsers and normalisation on OCI Container Instances, per-second billing

Three rules baked into the design

  • The exam path never sleeps. auth-node, student-node and fast-api stay warm during exam hours — 3.3 s cold versus 8 ms warm is why.
  • App and database stay together. Documented N+1 patterns turn a 2 ms hop into 100 ms+ per page. If the database moves, the applications move with it.
  • Capacity leads demand. Scale from the assessment schedule table 20 minutes ahead, not from CPU metrics after the fact. Zero cold start — better than serverless.

Plan B in detail — Google Cloud Run, asia-south1

A fully serverless target: request-driven containers, managed database, no cluster to operate. It meets both hard requirements — but the cost depends entirely on whether the queue engine is also rewritten.

The blocker that decides the price: BullMQ. Cloud Run bills a container only while it is handling a request. A queue worker blocking on Redis is not handling a request — so it must run with CPU always allocated and min-instances=1, which is a virtual machine at roughly twelve times the price. Escaping that means rewriting BullMQ to Cloud Tasks or Pub/Sub push so workers become request-driven — which changes the retry and back-off semantics assessment scoring depends on.

Performance guardrails & rollback

Requirement 2 says performance must be no worse than today. These criteria enforce it, and they apply to both plans. If a guardrail breaches, restore the previous node count or instance shape immediately, then investigate — never debug in a degraded production state.

  • API p95 latency does not worsen by more than 10% against the week-1 baseline
  • Error rate and timeout rate do not increase
  • No sustained node CPU above 70–75% after right-sizing
  • No OOM kills, memory pressure or unexpected pod eviction
  • Database connections stay below 70% of the configured limit
  • Queue delay and assessment processing time do not materially increase
  • Login, assessment, scoring, proctoring and dashboard smoke tests all pass
  • Every capacity change has a written, tested rollback before it starts

Observation windows: 48 hours after a node drain · 7 days after the database cutover · 48 hours before deleting any replaced resource.

What does not change under either plan: no reduction in production replica counts for customer-facing APIs · the proctoring and exam path stays warm during scheduled windows · all data stays in India · no production change without a captured baseline, acceptance criteria and a rollback · email, DNS and the observability stack are untouched.
