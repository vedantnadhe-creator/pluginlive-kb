# Assessment OTP Invite (account-less flow)

## What it is

A per-campaign mode for **corporate-assigned** assessments where the candidate does **not** need a PluginLive student account. They receive a single email containing an invite link, verify their email with a 6-digit OTP, and drop straight into the assessment runner.

Originally built for AI Interview. Generalized incrementally to all corporate-side assessment types: AI Interview, Communication, Aptitude, Hinglish, Custom (2026-06-10/11), then **Role-Based + Behaviour (2026-06-15)**. Each type is wired independently in its own `assign*Assessment` method — see Backend touchpoints.

Institute-side assessments still go through the portal-login flow.

## Admin trigger

`admin-react` Assessment Assignment screen has a corporate-only delivery checkbox. **As of 2026-06-11 the default is reversed: OTP invite is now the DEFAULT for corporate assignments.** The checkbox reads **"Send email & password instead (portal login, no OTP)"** — leave it **unticked (default)** for the no-login OTP invite (`is_otp_invite = true`); **tick it** to fall back to the legacy portal-signup + email/password reminder flow (`is_otp_invite = false`). Implementation: state `isOtpInvite` defaults to `true`, is reset to `true` whenever the entity switches to corporate (`false` for college), the checkbox is rendered `checked={!isOtpInvite}` / `onChange={e => setIsOtpInvite(!e.target.checked)}`, and the payload still sends `isOtpInvite` (true = OTP). The flag is round-trippable so resends and post-hoc listings stay consistent.

## Data model

### Postgres — single column

```sql
ALTER TABLE assessment.assessment_corporate_map
  ADD COLUMN is_otp_invite BOOLEAN NOT NULL DEFAULT false;
```

- One row per corporate campaign; the flag lives at campaign granularity, not per-student.
- `DEFAULT false` → zero backfill, every existing campaign keeps its legacy behavior.
- No new tables, no enum changes, no new indexes.
- DB-Scripts: `Assessment OTP Invite/001_corporate_map_is_otp_invite.sql`.

### MongoDB (user-management-node) — generalized OTP store

- Old: `ai_interview_invite_otp` collection + `AiInterviewInviteOtp` model + `aiInterviewOtpHandler` + `/public/interview-otp/*` routes.
- New: `assessment_invite_otp` collection + `AssessmentInviteOtp` model + `assessmentInviteOtpHandler` + `/public/assessment-otp/*` routes.
- The old paths/models are **kept as thin aliases** for backward compatibility — already-issued AI Interview invite links keep working.
- The OTP record stores: hashed OTP, expiry, `assessment_assigned_id`, `assessment_type`, `email`, attempt counter, resend timestamp.

## Email flow

When `is_otp_invite = true` the admin-node assignment handler **suppresses both** the portal-signup email and the legacy "complete your assessment" reminder, and sends only the OTP invite-link email.

The invite-link email template lives at `user-management-node/src/utils/emailTemplates/assessmentInviteOtp.js` (renamed from the AI-interview-specific template). It carries: candidate name, assessment name (resolved live), corporate name, link to `/assessment/start/<token>`, expiry window.

The same link can be copied manually from the admin assessment detail **StudentsTable** (Copy Link action) and shared via WhatsApp/SMS. This is a fallback for failed email delivery and reuses the same OTP-invite flow — the candidate still verifies email with a 6-digit OTP before entering the assessment. See `Assessment/admin-frontend.md` for the institute equivalent (activation link).

The invite URL is built from `process.env.ASSESSMENT_FE_BASE_URL` (admin-node helper `app/helpers/assessmentInviteEmail.js`). Each environment **must** set this — the helper falls back to `https://assessment.dev.pluginlive.com` if unset, so a UAT or PROD container without the var silently sends candidates to DEV. UAT value: `https://assessment.uat.pluginlive.com`. PROD value: `https://assessment.pluginlive.com`.

## SMS channel — OTP also texted via MSG91 (2026-07-09)

The **same** verification OTP is now also delivered by **SMS via MSG91**, as a **best-effort second channel** alongside the email. Email remains the source of truth; SMS never blocks or fails the request.

- **Where:** `user-management-node` `assessmentInviteOtpHandler.requestOtp` (and `/resend`). After the email is dispatched, it looks up the candidate's phone and texts the same code. `verifyOtp` is unchanged — one hash validates a code read from either channel.
- **Sender:** `user-management-node/app/helpers/msg91Sms.js` → `sendOtpSms({to, otp})` POSTs to MSG91's **Flow API** (`https://control.msg91.com/api/v5/flow/`) with `{ template_id, recipients:[{ mobiles, var: otp }] }`. Reuses the WhatsApp helper's `normalizeRecipient` (India +91). Reuses the existing `MSG91_AUTHKEY` (same MSG91 account `pluginlive5` as WhatsApp).
- **Phone source (2026-07-09):** captured on the **admin** side at candidate-add time — the account-less OTP candidate never has a user record, so a `users.phone_number` lookup finds nothing. An **optional "Mobile Number"** field was added to admin-react's Add-Candidate form and the bulk CSV (`mobile_number`/`mobile`/`phone`/`contact_number` headers) in `EnhancedBulkUploadDrawer.js`; the value rides on the candidate object into `studentsData`/`bulkUploadData` (`AssessmentSelect.js` maps carry `phone`). admin-node's `getAssessmentAssignedParticipants` (corporate branch) and the async job payload (`__phone`, alongside `__name`) thread it, and it is **minted into the invite JWT as a `phone` claim** by `mintInviteToken`/`buildInviteUrl`/`sendAssessmentInviteEmail` across **every** OTP-invite path (AI_Interview/Communication/Aptitude/Custom/Behavior/Role_Based — sync mint sites *and* the async `assignmentWorker` OTP branch). UMS `requestOtp` then reads `invite.phone` first, falling back to the `users.phone_number` lookup (encrypted, decrypted via `MASKING_SECRET`, matched case-insensitively by email) for older tokens/other flows. The candidate screen still asks for **email only** — no phone is entered there. Phone is **optional** end-to-end: absent → email-only, nothing breaks. No column added to `assessment_invite_otps`, no DB migration.
- **Phone is now persisted to the student profile (2026-07-10).** The entered mobile is written into the silent OTP candidate's `student.student_personal_profile.contact_number` at provisioning — the `admin.phoneNumber` in the `buildPayload`/`buildAiInterviewStudentPayload` provisioning payloads was hardcoded `""`; it now sources `student.phone`/`s.phone`/`cand.phone` (from `getAssessmentAssignedParticipants`, which carries `phone`). `createPublicStudent` (student-node) maps `admin.phoneNumber → studentPersonalProfile.phoneNumber → spp.contact_number`. Effects: (a) the assessment student list's **CONTACT DETAILS** column (reads `spp.contact_number`) now shows the number instead of `-`; (b) the number is resolvable by email for any downstream reader.
- **Copy Link now carries the phone for ALL assessment types (2026-07-10).** `getAssessmentInviteLink` (`Assessment.js`) LEFT JOINs `student.student_personal_profile` on `primary_email` and passes `phone: spp.contact_number` into `buildInviteUrl` → the copy-link token gets the `phone` claim, so SMS OTP fires for every type opened via Copy Link (previously only the assign-time email path — effectively Communication — carried it). NB: only applies to candidates whose profile has a phone (i.e. added via the mobile field going forward; ~8k pre-existing accounts already have `spp.contact_number`).
- **Admin UI (2026-07-10):** the Add-Candidate drawer shows the mobile in the candidate card list and a **Mobile** column in the candidate table (`EnhancedBulkUploadDrawer.js`).
- **Role_Based & Custom_Assessment did NOT get SMS (fixed 2026-07-13).** Their corporate-OTP branches explicitly **"do not create student accounts"**, so — unlike AI_Interview/Communication (which provision a silent profile) — there is **no `student_personal_profile`** row, so the profile-based phone lookup (Copy Link's `spp` join, CONTACT DETAILS) found nothing and SMS never fired via Copy Link. Fix: a nullable **`contact_number` column on `assessment.assessment_assigned_students`** (migration `Assessment OTP Invite/…__assigned_students_contact_number.sql`; Prisma `AssessmentAssignedStudent.contactNumber` in admin-node + student-node) is populated from `candidate.phone`/`student.phone` at the RB (`generateRoleBasedQuestions.js`) and Custom (`customAssessment.js`) assign create sites. `getAssessmentInviteLink` (Copy Link) and both student-list queries now read **`COALESCE(aas.contact_number, spp.contact_number)`** — so the phone resolves for profile-less types (RB/Custom via the row) and profile types (AI/Comm via `spp`) alike. Custom provisioning `phoneNumber` (was `""`) also now sources the candidate phone. DEV+UAT live 2026-07-13; only new assigns populate the column (no backfill).
- **Custom_Assessment is ASYNC — needed a separate fix (2026-07-13).** `Custom_Assessment` corporate is async-enabled (`AssignmentJobService.isAsyncEnabled` → true for Custom corporate), so its `assessment_assigned_students` rows are created by the **queue worker's `assignmentDb.insertAssignedStudent`**, NOT the sync `createMany` — so the sync-path `contact_number` populate never ran for Custom, and (being account-less/no profile) Copy Link/CONTACT DETAILS/SMS stayed empty. Fix: the Custom async job item now carries `__phone` (`customAssessment.js`), `insertAssignedStudent` accepts + inserts `contact_number`, and the worker's assign stage passes `item.studentPayload.__phone`. Now every async assign row (Custom + also AI/Comm/Aptitude) stores the mobile. Role_Based is unaffected — it uses its own set-group `prisma.create` path, not the queue worker.
- **Pre-fix rows can't be fully backfilled.** Role_Based saves its roster (with phone) in `student_lists.students_data`, so old RB rows were backfilled by email (`UPDATE … FROM jsonb_array_elements(students_data)`). Custom does NOT persist a roster, so a pre-fix Custom candidate's phone is unrecoverable — those need a fresh assign. New assigns populate `contact_number` automatically.
- **Still not sourced:** the drop-off **resend** reminder path (`resendInvitesToStudents`) — lower priority; falls back to the user-record lookup.
- **`SMS_ENABLED` master switch:** only the literal string `"true"` enables SMS; anything else (unset / `"false"`) skips the lookup+send entirely and keeps the flow email-only. Read per-request, so it can be flipped by env without a redeploy.
- **Response additions (backward compatible):** `/request` & `/resend` now also return `sms_sent: boolean` (a phone was on file and an SMS was dispatched — **not** a delivery guarantee) and `masked_phone: string|null` (last-4 masked, e.g. `••••1234`; full number never returned).
- **Frontend hint:** `Assessment-React` `InviteStart` OTP screen appends "and texted to **••••1234**" to the "Code sent to &lt;email&gt;" line **only** when `sms_sent` is true; email-only candidates see the unchanged copy.
- **DLT is mandatory for delivery (external, not code).** MSG91's Flow API returns `type:"success"` on **acceptance into the queue** — that does **not** mean delivered. Indian carriers reject via DLT unless (1) the SMS template is **DLT-approved** (MSG91 shows "Verified by DLT"; template `6a4deb0448d912e6610658e3`, sender **PILTEC**, DLT template `1707167757323433650`) **and** (2) the **PE-TM chain** is Active on the DLT operator portal — for MSG91 the telemarketer is **Walkover Web Solutions**, TM ID **`1302157225275643280`** (added via the DLT portal's "Telemarketer Request", accepted by MSG91, then chain approved). A missing chain surfaces in MSG91 Delivery logs as **"PE-TM Chain Error on DLT"**. Both were completed for `pluginlive5` on 2026-07-09.

## Candidate flow

1. Candidate opens `assessment.<env>.pluginlive.com/assessment/start/<token>`.
2. Assessment-React `InviteStart` component prompts for email → calls UMS `/public/assessment-otp/send` → 6-digit OTP delivered.
3. Candidate enters OTP → `/public/assessment-otp/verify` → UMS mints a scoped JWT (`scope: "assessment:run"`) carrying `assessment_assigned_id`, `assessment_type`, `email`, `role`, `company`. **TTL = the portal login token lifetime** (`SCOPED_JWT_TTL = server.LOGIN_TOKEN_EXPIRES_IN`, currently `43200000` → parsed by jsonwebtoken's `ms` as 43.2M **ms** = **~12h**). Previously this was hardcoded to `"2h"`, which expired mid-attempt on long assessments (Communication/Hinglish with video upload) and surfaced as a `401` on **every** authed call — `heartbeat`, `saveResponse`, `uploadVideo`, `submitAssessment` — with a "Failed to submit assessment: Request failed with status code 401" alert. Bumped to match login 2026-06-15 (sourced from the same config so the two stay in sync). The scoped token has no refresh; an attempt still must complete within the TTL window from OTP verification.
4. `student-node` `/ai-interview/invite/resolve` (generic despite the legacy path name) reads the corporate map + assessment row, returns the **real assessment name**, the type-specific runner config, and the assignment's **`status` + `submitted`** (added 2026-06-15 — see "already-submitted gate" below).
5. Assessment-React `InviteAssessmentRunner` dispatches to the matching `*assmt` partial (Communication, Aptitude, Role-Based, Behaviour, Custom, AIInterview). **`Hinglish` is folded onto the Communication runner** (2026-07-03) — it is not a real type, just Communication with `response_language=Hinglish`, so it must not mount the legacy `Hinglishassmt` fork (see gotcha). The runner title shows the real assessment name (not "AI Interview").
6. On completion, the candidate **stays on the terminal Thank-You screen** ("You can now close this window"). There is **no post-completion redirect** — the OTP `sessionStorage` is left intact. (Previously a "Back to Home" button cleared the scoped JWT and hard-redirected to `/assessment`; with the JWT gone `AuthRouter` fell through to `AuthPage`, which auto-fires `window.open(AUTH_URL)` on mount — so finishing an invite interview bounced the candidate to the portal login page. Fixed 2026-06-15 by removing the button.)

### Already-submitted gate (re-login no longer reopens a finished interview)

A candidate who re-opens their invite link (or re-verifies OTP) after submitting must **not** be put back into the interview. As of 2026-06-15:
- `resolveInvite` returns `status` (`PENDING`/`INPROGRESS`/`COMPLETED`/`DROPOUT`) and `submitted` from `assessment.assessment_assigned_students`.
- `InviteStart` checks these on mount: when `status === 'COMPLETED'` (or `submitted === true`) it renders an **"Interview already submitted"** screen instead of the email/OTP wall.
- Server-side backstop: `student-node` `startSession` returns **409** if the assignment is already `COMPLETED`/`submitted` (a fresh `AIInterviewSession` is never created). `INPROGRESS` resumes are unaffected.

## Backward compatibility checklist

- Existing AI Interview invites continue to work via the `/public/interview-otp/*` and `aiInterviewInviteOtp` aliases.
- Every existing corporate campaign has `is_otp_invite = false` after backfill (NOT NULL DEFAULT false), so portal-signup + reminder behavior is unchanged for them.
- Institute campaigns are untouched — the column does not exist on `assessment_institute_map`.
- **AI Interview is the special case — no `is_otp_invite` checkbox.** Unlike the other corporate types (which are OTP only when the admin ticks the box, gated via `is_otp_invite`), AI Interview never had the flag and was **unconditionally OTP for every assignment, corporate *and* institute**. As of **2026-06-17** `assignAIInterviewAssessment` branches on `isCollege`: **corporate → OTP invite** (unchanged), **institute → normal student-portal flow, no OTP** (new students get the activation email only; existing students get the assessment reminder via `sendRemindersToStudents` only — split by new-vs-existing like Communication). See [ai-interview.md](ai-interview.md) "Invite delivery splits by entity type". So institute AI Interview candidates now use the portal like any other institute assessment.

## Known gotchas (carried over from build)

- **`ASSESSMENT_FE_BASE_URL` env var.** Without it, the admin-node helper falls back to the DEV URL — UAT and PROD admin-node `.env.<env>` files must include the matching frontend base URL or every invite email links candidates to DEV.
- **Fastify body schema strips unknown fields.** `admin-node` `assignAssessmentSchema` must explicitly list `isOtpInvite` or the handler never sees it (server logs the row with `is_otp_invite = false` even though the request carried `true`). Same applies to any future toggles added on this form.
- **`admin-react` `filterAssessmentData`** rebuilds the payload from a whitelist before submit. Any new field on the form must be added there or it silently disappears.
- **Title is dynamic, not hard-coded.** `resolveInvite` returns the campaign's real assessment name; the runner uses it for the instructions header. Old caches on the client can still show "AI Interview" — a fresh OTP verify rewrites the `sessionStorage` entry, so retesting requires reopening the invite link.
- **Per-type OTP wiring is not automatic.** A new corporate assessment type does NOT get OTP invite for free: its `assign*Assessment` method must (1) thread `isOtpInvite`, (2) set `isOtpInvite` on the corporate map create, (3) skip account creation + portal/reminder emails when on, (4) send `sendAssessmentInviteEmail` per candidate with the correct `assessmentType` claim, AND the FE `InviteAssessmentRunner` `TYPE_MAP`/`switch` must include that type string — otherwise the candidate hits "Unsupported assessment".
- **Resend-invite / send-reminder must respect the campaign mode (fixed 2026-06-17).** The admin drop-off **resend** (`/assessment/resendInvites` → `Assessment.resendInvitesToStudents`) and **reminder** (`/assessment/sendReminders` → `sendRemindersToStudents`) in `admin-node` originally sent the wrong email for corporate: (a) for OTP campaigns they sent a portal reminder instead of the scoped OTP link, and (b) `resendInvitesToStudents` omitted `isCorporate` in the `resendAssessmentInvite` payload, so the UMS `assessmentRemainder` handler fell through to the **institute-reminder** template instead of the corporate **login email+password** template (`assessmentStudentCorporate2`). Both methods now read `assessment_corporate_map.is_otp_invite` and branch: corporate+OTP → `sendAssessmentInviteEmail` (scoped `/assessment/start` link, `assessmentType` = DB `type_name`); corporate+portal → reminder with `isCorporate:true` (UMS sends email+password); college → institute reminder. NB: `resendInvitesToStudents` also **resets** the dropped assignments (new set, deletes old answers/scores/proctoring) before emailing — never invoke it as a dry test.
- **Add-students-to-existing campaign must respect the mode too (fixed 2026-06-19).** Adding candidates to an already-created campaign (`/assessment/addStudentsToAssessment` → `Assessment.addStudentsToExistingAssessment` → `_addStudentsToOneTimeAssessment`) was OTP-unaware: it always created a portal student account (so `createPublicStudent` sent the activation/credentials email) **and** sent `sendRemindersToStudents` to pre-existing candidates — never the scoped OTP link. So adding a student to an existing corporate OTP campaign (e.g. AI Interview) emailed **login credentials instead of the OTP invite**. Now the one-time add flow detects OTP via the shared predicate **`admin-node/app/helpers/otpInviteCampaign.js` → `isCorporateOtpInviteCampaign({isCorporate, isOtpInvite, assessmentTypeName})`** = `isCorporate && (is_otp_invite || assessmentTypeName === 'AI_Interview')` — AI Interview corporate is always OTP yet keeps `is_otp_invite=false`, so the flag alone is insufficient. When OTP: new accounts are created **silently** (`skipActivationEmail: true`) and `sendAssessmentInviteEmail` (scoped link, `assessmentType` = DB `type_name`, `role:null`) is sent to **every** added candidate — both brand-new and pre-existing; the portal reminder is skipped. Non-OTP corporate and all institute flows are unchanged. This predicate is the single source of truth shared by the assign/resend/add paths; any future add/clone path should call it rather than re-deriving the condition.
- **Reload of an in-progress invite attempt = DROPOUT (fixed 2026-06-17).** The invite runner (`Assessment-React` `InviteAssessmentRunner`, route `/assessment/take/:id`) re-mounts on a browser reload / re-entry and used to re-show the instruction page, letting a candidate restart an attempt they had already begun. On mount it now calls `student-node` **`POST /students/assessments/invite/reloadGuard`** (public, like `getAssessmentQuestions`), which returns a `state`: `pending`/`resume` → render instructions; `completed` → "Already submitted"; `dropout` → "Assessment closed" terminal screen. For a non-resumable attempt already `INPROGRESS` the endpoint **atomically marks it `DROPOUT`**, so a reload cannot be used to retake. `is_practice` is never locked; diagnosis (institute map, no `scheduleId`) stays resumable. Applies to all OTP runner types (Communication/Hinglish/Aptitude/Custom/Behavior/Role_Based). AI Interview keeps its own resume flow (its runner is `/ai-interview/:id`, not this one). The FE guard fails open (transient error → `pending`), and the existing start-guard in `getAssessmentQuestions` (`RESUME_NOT_ALLOWED`/`ALREADY_IN_PROGRESS` 409) still backstops the actual question fetch.
- **Role-Based has TWO assign code paths — admin-react uses the set-group one.** (1) The direct `assignRoleBasedAssessment` → `createRoleBasedAssessment` path (wired for OTP earlier 2026-06-15) is **NOT** what the admin UI calls. (2) admin-react filters Role-Based out of the direct "Send" flow and routes it through **Generate Test (`initiateRoleBasedGeneration`) → Review Panel → `assignStudentsToGroup` → `AssessmentSetGroupService.assignStudents` → `processStudentsForAssessment`**. Wiring only the first path looks correct in code review but does nothing for real assignments. - **Scoped JWT TTL = login token lifetime.** `SCOPED_JWT_TTL = server.LOGIN_TOKEN_EXPIRES_IN` in `assessmentInviteOtpHandler.js`. If `LOGIN_TOKEN_EXPIRES_IN` is **unset** in a given env, the value resolves to `undefined` → jwt.sign mints a **non-expiring** token; every env's UMS `.env` must keep this var set (UAT/DEV = `43200000` → ~12h). It must be a *string* (env vars always are) so jsonwebtoken's `ms` parses it as milliseconds; a bare number would be treated as seconds.
- **Frontend `process.env` in `aiInterviewInviteAPI.js` — TWO opposite failure modes (resolved 2026-06-15).** The invite *email link* was always correct (`assessment.uat...`), but after landing the invite/AI-interview flow misbehaved depending on how the module read its axios base URLs:
  1. **Member access** `const API_URL = process.env.API_URL` with `|| 'https://api-auth.dev.pluginlive.com/'` / `|| '...api-std.dev...'` fallbacks → in this webpack build the member-access token was **not inlined**, so `API_URL`/`STD_API_URL` were `undefined` at runtime and the **DEV fallback fired → candidates bounced to DEV** (page loaded fine, wrong env). The dev string surviving in the bundle (not folded away by terser) is the tell.
  2. **Named-key destructuring** `const { API_URL, STD_API_URL } = process.env` → URLs **did** inline correctly (no DEV leak), BUT webpack left a **dangling `process.env;` expression statement** that terser did not eliminate. At runtime `process` is undefined → **`Uncaught ReferenceError: process is not defined` → blank screen** on the invite entry page. (The tiny `src/utils/*Request.js` files use this same destructuring safely because the binding is their only statement and the declaration gets fully DCE'd; a larger module like this one keeps the dangling reference.)
  - **Final fix:** do **not** touch `process.env` in this chunk at all. Reuse the shared, already-configured axios instances: `import authRequest from 'utils/authRequest'` (→ `API_URL` / api-auth / UMS, for the public OTP endpoints) and `import studentRequest from 'utils/studentRequest'` (→ `STD_API_URL` / api-std, which also attaches the invite scoped JWT from `sessionStorage` that the resolve call needs). Their base URLs inline cleanly and no `process.env` reference is left in the module.

- **Scoring must tolerate the missing student profile (fixed 2026-06-17).** Because an OTP campaign never creates a student account, the score-calculation cron's name lookup `getFullName(primaryEmail)` throws `"Student not found"` and the assignment ends up `calculation_error=true` with no scores — the symptom users report as "scores not calculating" for a Communication/Role-Based/Behaviour OTP invite. - **Scoped invite token must out-rank the portal default Authorization header (fixed 2026-06-11).** The runner's data calls all go through the shared `studentRequest` axios instance. When *any* portal session exists in that browser, `utils/initializeApp.js` sets `studentRequest.defaults.headers.common.Authorization` to the portal token. The interceptor originally injected the scoped OTP token only when *no* auth header was present (`hasAuth` checked the defaults too), so the **stale/expired portal default token shadowed the fresh 12h scoped token** → OTP assessment calls failed with `jwt expired` even though a valid scoped token was sitting in `sessionStorage`. This is the "login works but OTP expires" symptom (it bites when testing the invite link in a browser that's also logged into the portal). Fix: in an active invite session the scoped token (`assessment_invite_scoped_jwt` → legacy `ai_interview_scoped_jwt`) takes **precedence** over the portal default header; only an explicit per-request `Authorization` still wins. Normal portal students never have the scoped key set (written on OTP verify, cleared on completion), so they're unaffected. The backend scoped token itself was verified healthy — minted at 12h and accepted by student-node end-to-end on DEV & UAT — so this client-side precedence was the real remaining failure, not the token lifetime.
- **Wrong OTP must show "Incorrect code.", not bounce to the email step (fixed 2026-07-01).** `verifyOtp` posts to `/public/assessment-otp/verify` via the shared `authRequest` (UMS) instance, and a wrong/expired code correctly returns **HTTP 401** `{message:"Incorrect code."}`. But `Assessment-React/src/utils/initApiServices.js` registers a **global `authRequest` response interceptor** that, on *any* 401, did `localStorage.clear() + location.reload()`. So a wrong OTP reloaded the page → `InviteStart` remounted → `resolveInvite` → back to the **"Verify your email"** stage, and the candidate never saw the error. Fix: the interceptor now **skips the session-clear/reload for `/public/` endpoints** (unauthenticated — a 401 there is a bad code/link, never an expired session) and **rejects with the original axios error** instead of `new Error(error)` (the wrapper destroyed `error.response`, so `InviteStart`'s catch couldn't read `error.response.data.message`). `InviteStart.handleVerify` already renders `err?.response?.data?.message` in its OTP-stage `<ErrorBanner>`; it just never ran because the interceptor hijacked the 401 first. NB: OTP verify lives **only** in Assessment-React (`InviteStart` + `aiInterviewInviteAPI`), not student-react — the account-activation `CheckOtpPage` flow is a separate, unrelated screen.
