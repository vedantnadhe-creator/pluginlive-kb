# Drives Module

**Routes:**
- `/drives/role/:roleId` — Drive for a specific role (fresher)
- `/drives/:driveId/role/:roleId` — Specific drive for a role (fresher)

**Frontend:** `corporate-react-1/src/modules/Drives/`

## Overview

The Drives module manages placement drives — the scheduled evaluation events where corporates interview candidates from institutes. It provides drive-level candidate management, interview scheduling, evaluation forms, result uploads, offer management, conflict resolution, and bulk actions. This is the execution layer of the hiring pipeline.

## Key Features

- **Drive pipeline:** Create drive → Schedule interviews → Evaluate → Upload results → Offer
- **Fresher evaluation:** Route prefix indicates this is for fresher candidate drives
- **Bulk uploads:** CSV-based uploads for results, shortlists, offers, and assessments
- **Interviewer assignment:** Add interviewers to drives with time scheduling
- **Group discussion:** Dedicated GD round management
- **Conflict resolution:** Resolve scheduling conflicts across drives
- **Candidate downloads:** Export candidate data from drives
- **Select Assessment:** In `IndividualDriveTable`, the `+ Select Assessment` button (rendered by `TableStatusIcon`) opens `SelectAssessmentDrawer` to map an assessment onto the selected candidates. The button and drawer are available on **every evaluation round** where the stage is not `all_candidates` or `offer` — i.e. Assessment, Group Discussion, Interview, etc. (Previously the drawer only mounted for `selectedRoundType.type === 'ASSESMENT'`, so the button did nothing on GD/Interview rounds — fixed so the drawer mounts wherever the button is shown.)
- **Assessment Status column & filter:** When the round being viewed has an assessment mapped to it, the evaluation table shows an **Assessment Status** column and a matching multi-select filter (`AssessmentStatusBadge` + `AssessmentStatusFilter` partial). Statuses: **Invite Pending** (mapped but invite not sent yet — no `assessment_assigned_students` row), **Pending** (invited, not started — also covers in-progress), **Dropped Off** (`DROPOUT`), **Completed** (submitted / scores calculated). Per-candidate status is sourced live from the Assessment DB via admin-node: corporate-node `getCandidateListForHR` → `AdminService.getCellStatusBundle` → admin-node `POST /corporate/:corporateId/cell-statuses` (model `Assessment.getCellStatusBundle`). For a round mapped to multiple assessments the status rolls up to the **most-progressed** one, so a single meaningful status surfaces: **Completed** wins over every lesser state. This matters because candidates are frequently invited to only *one* of the mapped assessments — the un-invited assessment has no `assessment_assigned_students` row and would otherwise yield a phantom **Invite Pending** that, under the old least-progressed rule, masked a real **Completed** (the candidate read "Invite Pending" and the score column showed `NA` — see below). Most-progressed-wins ensures a candidate who finished any one of the mapped assessments reads **Completed** and their score shows. The response carries `assessment_status` per row plus a top-level `assessmentStatusColumn` flag that gates the column + filter. Filtering is server-side across all pages (handler resolves selected labels → allowed `student_id` list → SQL `AND jrsm.student_id IN (...)`, mirroring the Round Score filter). The flag is also set on the empty-result (`No candidate found`) early-return path — so filtering to a status with zero matches (e.g. `Completed` when nobody has completed) keeps the Assessment Status filter tab/column instead of dropping it and showing "No content".
- **NA assessment scores until Completed:** For an assessment-mapped round, the per-topic assessment **score columns render `NA`** until the candidate's `assessment_status === 'Completed'` (previously they showed a misleading `0` for candidates who had not started/finished). Completed candidates show real scores, including a genuine `0`. Sheet/manual (non-assessment) rounds keep their existing `0`-default behavior. Gate in `IndividualDriveTable` score-cell render: `candidateDeatils.assessmentStatusColumn && originalTopic === stage && row.assessment_status !== 'Completed'`.
- **Filtered evaluation export:** The evaluation-table export (XLSX / Google Sheet / CSV, `ViewDriveRole` → `handleExportClick`) honours the **candidates currently in view** — the active stage/filter/search and any explicit row selection — instead of dumping every applied candidate for the role. Resolution order in `handleExportClick`: explicit row selection (`selectedCandidateId`, the table `rowKey = student_id`) wins; otherwise `fetchBulkStudentIds()` resolves the full filtered set via the **same list source** the table uses (`getNewDriveFreshersList` → corporate-node `getCandidateListForHR` with `bulkDownload: true`, same payload as the displayed list). The resolved IDs are sent as `studentIds` to student-node `POST /students/role/:roleId/corporate/:corporateId/candidates/:downloadType/export`. This **resolve-then-export** design (rather than re-sending the raw filter object to the export endpoint) guarantees the export matches the displayed list 1:1 for **every** filter — including the ones resolved only inside corporate-node (Assessment Status, Round Score, Qualifying/Custom Questions, Work Experience) which the student-node export path does not re-implement. Backend: handler `exportCandidateList` already read `req.body.studentIds` and filters `getStudentDetailsForExport` by `id IN studentIds`, but the `candidateExportBody` schema was `additionalProperties: false` without `studentIds`, so the field was rejected — schema now declares `studentIds` (array of strings).
- **Filters survive sorting (and stage/status/search/tab changes):** The candidate-list refetch in `ViewDriveRole` runs from a `useEffect` keyed on `stage / searchValue / sortBy / status / panelValue / tabValue`. `getCandidateList(filterPayload, page)` only attaches the active filter to the request when a `filterPayload` is passed — it is guarded by `if (filterPayload) payload.filterPayload = filterPayload`. The effect previously called `getCandidateList()` with **no argument**, so on any sort (`onSorting` → `setSortBy` → effect fires) the guard was skipped, `payload.filterPayload` was dropped, and the server returned the unfiltered list — i.e. clicking a column sort silently cleared the user's applied filter. Fix: the effect now passes the currently-applied filter, `getCandidateList(selectedFilterValue || {})`, matching the other refetch call sites (pagination, status-change, conflict-resolution). `selectedFilterValue` is intentionally **not** in the effect's dependency array — applying a filter already triggers its own explicit fetch (`applyFilter` → `getCandidateList(filterPayload, 0)`), so adding it would double-fetch; the effect closes over the latest value on each sort instead.
- **Cancel-filter must reset to `{}` not `[]` (avoids `body must be object`):** In `DriveFilter` (`ViewDriveRole/IndividualDriveTable/DriveFilter/index.js`), `onCancelFilter` reset the applied-filter state with `setSelectedFilterValue([])` — an **array** — while the state is otherwise always an object (`useState({})`, reset `{}`). The cancel's own refetch (`getCandidateList({}, 0)`) is fine, but the array lingered in `selectedFilterValue`, and the *next* sort/stage/tab refetch — which after the "Filters survive sorting" change passes `getCandidateList(selectedFilterValue || {})` — sent it into `corporateRequest.post(url, filterPayload || {})`. Since `[]` is truthy, `[] || {}` stays `[]`, so the request body of corporate-node `POST …/candidate/list` is an empty **array** → Fastify rejects it with `400 FST_ERR_VALIDATION` **`body must be object`**. Repro: apply a filter → **Cancel** → click a column sort. Fix (corporate-react only, two layers): `onCancelFilter` now resets `setSelectedFilterValue({})`, and `getNewDriveFreshersList` (`Drives/actions.js`) coerces any non-plain-object body (null/undefined/array) to `{}` before `corporateRequest.post` as defense-in-depth, so a stale array filter state can never produce a non-object body again.
- **Candidate-list SQL: `ORDER BY` must follow all `WHERE` fragments (sort + filter):** corporate-node `DriveRoleCandidateMap.getCandForHR` builds the candidate list as one `$queryRaw` whose `WHERE` is assembled from ~30 optional `Prisma.sql` fragments (search, stage, score, college, gender, questions, `assessmentScoreStudentIdQuery`, `assessmentStatusStudentIdQuery` = `AND jrsm.student_id IN (...)`, etc.), followed by `OFFSET/LIMIT`. The sort fragment `orderCondition` (`ORDER BY ...`) was interpolated **mid-`WHERE`**, before several of those `AND ...` filter fragments. With an active sort + any of those filters, the SQL became `... ORDER BY <col> asc NULLS LAST AND jrsm.student_id IN (...) OFFSET ...` → Postgres `42601` / Prisma `P2010` **`syntax error at or near "AND"`**. Sort-only or filter-only requests happened to stay valid, which is why it surfaced only when sorting a filtered list. Fix: `orderCondition` is now interpolated **last**, immediately before the `OFFSET/LIMIT` fragment, so the clause order is always `WHERE ... AND ... ORDER BY ... OFFSET LIMIT`. The sibling COUNT query (`SELECT COUNT(DISTINCT jrsm.id)`) never had an `ORDER BY` and lists the same filters correctly — it was the reference for the correct ordering.
- **Sorting an assessment-mapped round's score columns (Verbal/Reading/Listening/Writing/Total/CEFR):** For a round whose cell is mapped to a corporate assessment, the per-topic score columns are **not** stored in `job_role_student_map.parameters_score` — they live in the Assessment DB and are overlaid onto the *already-paginated* page in `applyAssessmentScoreOverlay`. So the SQL sort `ORDER BY (jrsm.parameters_score->'<round>'->>'<param>')::numeric` read all-`NULL` and sorting did nothing (clicking a score column header reordered nothing). Fix (corporate-node): `getCandidateListForHR` calls `resolveAssessmentSort` (helper `evaluationAssessmentOverlay.js`) when `sortType=param` on a concrete assessment-mapped round — it fetches every role candidate's scores (`AdminService.getCellScoresBundle` over the full applied-candidate email set), ranks them by the requested param (numeric, with a case-insensitive string fallback for `cefrLevel` bands), maps to an **ordered `student_id` list**, and passes it as `assessmentSortStudentIds`. `DriveRoleCandidateMap.getCandForHR` then orders by `array_position(ARRAY[...ordered ids...]::text[], jrsm.student_id) NULLS LAST` (unscored candidates sink to the bottom for both asc/desc, since direction is baked into the array order). Sheet/manual rounds are unchanged — they keep the `parameters_score` JSON sort. Falls back silently (no assessment sort) if admin-node is slow/unmapped (1s timeout).
- **Round Score filter by a sub-topic param (e.g. `readingAbilityScore ≥ 90`) on an assessment-mapped round:** The Round Score filter payload is `{ mode, scores: [{ topic:{name,score}, subTopics:[{param,score}] }] }`. For an assessment-mapped round the whole score entry is stripped from the SQL (`parameters_score` is empty for it) and resolved in `resolveAssessmentScoreFilter` → allowed `student_id` list. That resolver previously evaluated **only** the round-level `topic.score` overall threshold and **ignored `subTopics` entirely**, so a per-parameter threshold (with `topic.score = 0`) matched everyone — the sub-topic filter was silently dropped. Fix: `resolveAssessmentScoreFilter` now evaluates each `subTopics[]` threshold against the flattened Assessment-DB scores (ANDed together, honoring `selection` `>=` / `rejection` `<=`), and only applies the round-level score when `> 0` (mirroring the SQL's `if (item.topic.score)` guard). Result intersects into `assessmentScoreStudentIds` → SQL `AND jrsm.student_id IN (...)`. Sheet rounds still filter via the SQL `parameters_score->'<round>'->>'<param>'` path (unmapped rounds are left in `body.scores`).
- **CEFR Level filter is ordinal, not numeric:** `cefrLevel` values are CEFR bands (`A1 < A2 < B1 < B2 < C1 < C2`), so the generic numeric sub-topic path broke it at every layer: the FE payload builder coerced every sub-topic value with `Number(item.value)` (`Number("A1")` → `NaN` → serialized `null`), and the backend resolver's `Number.isFinite` guard then dropped the entry — the CEFR filter silently matched everyone. Fix (both sides): **FE** (`corporate-react` `RoundsFilter`) renders the `cefrLevel` row as an Ant `Select` of the six bands (A1–C2, clearable) instead of the numeric text box, skips numeric validation for it, and the payload builder (`IndividualDriveTable`) sends the band **string** as `subTopics[].score`. **BE** (`corporate-node` `resolveAssessmentScoreFilter`) keeps `cefrLevel` entries whose value is a valid band (`CEFR_RANK` map + `cefrRank()`, case-insensitive) and compares candidates **by rank** — `selection` mode = candidate rank ≥ threshold rank, `rejection` = ≤; candidates with no CEFR level never match. Defensive guard in `DriveRoleCandidateMap.getCandForHR`: the raw-jsonb sub-topic SQL skips non-numeric scores so a stray ordinal value can't emit `::double precision >= NaN` (invalid SQL → 500). CEFR always comes from a Communication assessment, so in practice it is always resolved on the Assessment-DB overlay path, never the SQL path.
- **Round Score filter labels are humanized:** `DriveFilter/Partials/RoundsFilter` rendered each sub-topic row using the **raw param key** (`item.topic`, e.g. `readingAbilityScore`) which the label CSS uppercased to an unreadable `READINGABILITYSCORE`. The raw key must stay as-is because it becomes `subTopics[].param` in the filter payload, so a **display-only `label`** field was added per row (`formatSubTopicLabel`: `readingAbilityScore → Reading Ability Score`, `cefrLevel → CEFR Level`, `englishVerbalScore → Verbal Score`, `overallScore → Overall Score`, else camelCase-split) and the column renders `record.label`. Mirrors the candidate table's own `formatSubTopicLabel`.
- **Total Score & CEFR Level columns render right after Assessment Status:** In `IndividualDriveTable` the round's sub-topic columns are built from the backend `topics[].subTopic` order (Communication schema: verbal, reading, listening, writing, totalScore, cefrLevel). The two headline columns now float to the front of that block via `HEADLINE_SUBTOPICS = ['totalScore','cefrLevel']`, so on a round tab the order after **Assessment Status** is **Total Score → CEFR Level → Verbal → Reading → Listening → Writing**. Presentation-only; backend contract unchanged.
- **Export disabled when zero candidates:** The export icon (`AtsExportIcon`) is disabled when there are no candidates to export — either the stage is empty (`getStageCount() === 0`) **or** the active filter/search narrowed the current view to zero (`count` / `notDisabledCount` / `totalCount` on `candidateDeatils` all `0`/absent). Click is a no-op while disabled (`if (isDisabled) return`).
- **College Name & Location filter — recover college/state/city when `institute_campus_id` is nulled:** The "College Name & Location" filter (`DriveFilter/Partials/CollegeLocation`, options from `GET /corporate/eligibilityCriteria/role/:roleId/college/filter` → `eligiblityCritriaFilterHandler.getCollegeDetailsFilter` → `eligiblityCertriaFilter.getCollegeDetailsList`, returns `{ states, cities, collegeNames }` each `[{id,name}]`) derived all three lists **only** by joining `institute.institutes_campuses ic ON ic.id = student.students.institute_campus_id`. The **current-course feature nulls `students.institute_campus_id`** while keeping the canonical name in `students.institute_campus_name` (== `institutes_campuses.campus_name` for ~98% of rows; the integer `students.current_state` and `student.current_course.state/city` are **not** reliable sources — current_course is populated for only ~10% of rows). So for any FK-nulled candidate the campus join matched nothing and **College Name, State and City all came back empty** (e.g. a drive with a single such candidate showed three empty dropdowns). **Fix (corporate-node, raw SQL only):** each option list is now the `UNION` of (1) campuses reached via the live FK and (2) campuses **re-resolved by canonical name** (`ic.campus_name = s.institute_campus_name`) when `NULLIF(TRIM(s.institute_campus_id),'') IS NULL`; College Name adds a third branch returning the **raw free-text name** (`id = name`) when the name matches no campus (so genuinely-unnormalized names like a test "prabha college crew" still appear, just without state/city). The candidate **list + count** filters in `DriveRoleCandidateMap.getCandForHR` apply the selected state/city/college via a **fan-out-safe `EXISTS`** that resolves the campus by FK **or** canonical name (a plain join on `campus_name` would duplicate rows — ~6.8k campus names are non-unique), and college also matches the raw `institute_campus_name`. Also fixed a latent bug there: the city and college filters were both assigned to `collegeStateQuery`, clobbering the state filter and each other (now `collegeCityQuery` / `collegeQuery`). The name match is **case/whitespace-insensitive** (`LOWER(TRIM(ic.campus_name)) = LOWER(TRIM(s.institute_campus_name))`) — an exact `=` missed ~136 FK-nulled candidates on UAT whose stored name differed from the canonical campus only by case or trailing spaces. Backed by two indexes on `institute.institutes_campuses`: `idx_institutes_campuses_campus_name` (plain, migration 002) and `idx_institutes_campuses_campus_name_lower` on `LOWER(TRIM(campus_name))` (functional, migration 003 — the one the name match actually uses), both DB-Scripts `Corporate Drive Metrics Performance/`, DEV+UAT applied, PROD pending, so the name match stays cheap in the per-row `EXISTS`. No student-node/snapshot change is needed — the canonical name carries the link. **Limit:** candidates whose `institute_campus_name` matches **no** campus at all (genuinely free-typed text that was never normalized, ~397 on UAT) have no location anywhere (campus FK nulled, `current_course`/personal-profile/`current_state` empty) and cannot be resolved by any query — they need the name corrected to a real campus or upstream entity-normalization at ingestion.
- **College Name options are de-duplicated by name (case-insensitive):** A college such as **Christ University** has several `institute.institutes_campuses` rows sharing one `campus_name` (different cities, and sometimes different casing — `Christ University` vs `christ University`). The College Name dropdown was keyed by **campus id**, so the same name rendered once per campus row (the reported "Christ University ×3"); the name-resolution join made it worse since a single name-only candidate fans out across every same-named campus. Fix (`getCollegeDetailsList`): options are now grouped on `LOWER(TRIM(campus_name))` with one representative display name (`MIN(name)`), and the option **value (`id`) is that lower/trimmed key** — so the list shows each college once. The candidate list/count college filter (`DriveRoleCandidateMap`) matches `LOWER(TRIM(s.institute_campus_name)) IN (collegeIds)` **OR** the resolved campus `LOWER(TRIM(ic2.campus_name)) IN (collegeIds)`, so one "Christ University" selection still matches candidates at **any** of its campuses, any casing (served by the `…campus_name_lower` functional index). State/City are unaffected — they key on the stable `state_id`/`city_id`, which don't duplicate per name.
- **Schedule drawer — Note/Instructions is mandatory & flows into the candidate WhatsApp:** In the Drive **Schedule** drawer (`Drives/ViewDriveRole/BulkActionDrawer/ScheduleInterviewDrawer`), the **Note/Instructions** field (form field `instructions`, "Visible to the candidate") is now **required** — `InterviewForm.js` marks the label with `*` and adds a validator rejecting empty/whitespace, so the form (`scrollToFirstError` + `onFinish`) blocks scheduling until a note is entered. On confirm, the drawer's `onSubmitFormData` (`index.js`) fires the candidate notifications: email via `OnlineScheduleTemplate`/`OfflineScheduleTemplate`, and WhatsApp via `sendNotificationBulkEmailWhatsapp` using the Interakt templates **`corporate_online`** (online / `EXTERNAL_LINK` mode — params: company, role, type-label, date-range, time, **link**, **note**) and **`corporate_offline`** (all offline modes — params: company, role, type-label, date, time, **location**, **note**). The note (`payload.instructions`) is the **last (7th) body parameter** in both templates; both Interakt template bodies must have 7 `{{n}}` placeholders or the send is rejected. WhatsApp only goes to candidates with a `phoneNumber`. The **candidate schedule email** also renders the note — `OnlineScheduleTemplate`/`OfflineScheduleTemplate` take a `note` prop (passed as `note: payload.instructions` at all four email dispatch sites: assessment-online, assessment-offline, interview-online, interview-offline) and show a **Note/Instructions** line (rendered only when non-empty, `white-space: pre-wrap`). **Provider-template gotcha (live UAT):** the MSG91/Interakt `corporate_online` and `corporate_offline` templates were originally approved with **6** placeholders; sending 7 makes MSG91 bounce async in the delivery report with error **132000** "localizable_params (7) does not match expected (6)" — the send returns a synchronous `{status:"success", data:"...in process..."}` regardless, so param-count failures only show up as non-delivery. Adding the 7th `{{7}}` placeholder to **both** templates on the provider (and re-approval) is required for the WhatsApp note to actually deliver; the email path is unaffected.
- **Age filter — whole-year vs Strict (years + months):** The Age filter (`DriveFilter/Partials/AgeFilter/AgeFilter.js`) derives age live from `student_personal_profile.dob` (`spp.dob`, a TEXT column) in corporate-node `DriveRoleCandidateMap.getCandForHR`. **Default (non-strict):** From/To are whole years and the SQL compares completed years — `EXTRACT(YEAR FROM AGE(CURRENT_DATE, spp.dob::date)) BETWEEN ${fromAge} AND ${toAge}` (or `<= toAge` when From is invalid). Because only whole years count, an upper bound of `22` includes everyone from `22y0m` to `22y11m` (a candidate isn't dropped until `23y0m`). **Strict mode (opt-in checkbox "Strict (consider months)"):** reveals a Months (0–11) input beside each year box; the FE sends `strictAge: true` plus `fromAgeMonths`/`toAgeMonths` = `years*12 + months`, and the SQL switches to total-month comparison — `(EXTRACT(YEAR FROM AGE(...))*12 + EXTRACT(MONTH FROM AGE(...))) BETWEEN ${fromAgeMonths} AND ${toAgeMonths}` — so months matter (e.g. To `22y0m` = 264 **excludes** `22y5m` = 269, but To `22y6m` = 270 includes it). Activation requires `toAgeMonths > 0`; the non-strict path is untouched when `strictAge` is absent (backward compatible — quick-select presets `≤22 / 21-22 / 22-25 / ≥25` stay year-only). Both paths keep the `spp.dob ~ '^\d{4}-\d{2}-\d{2}'` regex guard (junk/NULL DOB → `ELSE FALSE` → excluded while an age filter is active) and inclusive `BETWEEN` bounds. Note the regex only checks digit *shape*, so a malformed-but-shaped value (e.g. `2004-13-40`) passes the guard then fails `::date` → query error. Rides the same list query, so exports inherit strict-age automatically. Schema fields added to corporate-node `getCandidateListForHRBody`: `strictAge`, `fromAgeMonths`, `toAgeMonths`.
